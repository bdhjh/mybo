# AI 内容生产与发布自动化系统

一个在真实业务里长出来的内容系统。它不是一次设计完成的，而是在跑了三周之后，因为业务目标变了，被推倒重做了一次。

---

## 项目简介

需要持续产出面向计算机学生、科研人员和技术从业者的内容，分发到小红书和今日头条两个平台。

我负责把这件事从"人写、人发"变成一条流水线：

- 选题由人工确定，进入任务表；
- AI 完成资料研究、双平台写作、配图；
- 内容经过自动质检和外网预览页，交人工审核；
- 审核通过后，系统在指定时间自动发布到两个平台，并回填状态与链接。

系统由定时任务驱动，每小时轮询一次，人工只在两个节点介入：**命题**和**审核**。

---

## 为什么做这个系统

内容生产的问题不是"写不出来"，而是它是一条长链路，每一环都在消耗人力：

| 环节 | 人工做的问题 |
|---|---|
| 选题 | 靠临时起意，无法积累 |
| 资料研究 | 同一命题重复查资料 |
| 写作 | 同一内容要适配不同平台，容易变成复制粘贴 |
| 配图 | 临时找图，风格不统一 |
| 质检 | 平台限制（字数、符号、标题长度）事后才发现 |
| 审核 | 没有统一的审阅入口 |
| 发布 | 手动登录、复制粘贴、传图，重复劳动且易错 |

其中真正的成本不在"写"，而在**协调**：谁在什么时候做什么，做完交给谁，下一步由什么触发。

所以这个系统的设计重点不是"用 AI 写文章"，而是**把链路拆成有明确输入、输出和状态转移的节点**，然后决定哪些节点交给 AI、哪些交给脚本、哪些必须留给人。

## 系统演进

### Phase 1：新闻驱动

最初的形态是新闻驱动的：n8n（自建 Docker 服务，内含小红书/头条的发布 MCP）抓取互联网科技新闻、评分后写入飞书多维表，AI 再从表里取高分新闻写稿、发布。这是我在 2026-09-03 接手时，从表结构和总控文档还原出来的设计。

接手时的飞书表快照，能直接看到这一阶段的痕迹：

| 指标 | 值 |
|---|---|
| 表内记录 | 79 条 |
| 由 n8n 写入 | 70 条 |
| 带评分字段值 | 75 条（分值区间 35–96） |
| 来源 | 以 TechCrunch 为主 |
| 同时具备「内容栏目 + 目标读者」 | **4 条** |

也就是说：**绝大多数条目是自动导入的新闻，只有 4 条是可直接生产的命题**。

我在接手时确立的第一条原则就是"人工命题，AI 生产"——不自行大量抓取新闻作为选题，并把"自动新闻采集""RSS 自动选题"明确列入不做的清单。因此自动导入的新闻被闸门挡住：缺少栏目和目标读者的条目不进入生产，即使它有 96 分。

同期还有一次职责调整：n8n 退出发布环节，改由 WorkBuddy 接管（2026-09-03）。发布改为每小时轮询飞书表，用浏览器自动化直接发文。

这一阶段的链路：

```text
互联网新闻
    ↓
n8n 抓取 / 评分
    ↓
飞书多维表（任务 + 审核 + 状态）
    ↓
WorkBuddy 取高分命题
    ↓
AI 研究 / 双平台写作
    ↓
写回飞书 → 人工审核
    ↓
每小时轮询 → 浏览器自动发布
    ↓
小红书 / 今日头条
```

### Phase 2：从新闻驱动转向自主命题

2026-09-07 接入钉钉 AI 表格，09-08 全量切换，飞书链路转为只读归档。

**这不是换一个表格工具。** 数据形态的变化很清楚：

| | Phase 1（飞书） | Phase 2（钉钉） |
|---|---|---|
| 命题来源 | n8n 导入的新闻 | 人工命题 |
| 栏目 + 读者齐备率 | 4 / 79 | 98 / 98 |
| 评分字段 | 存在（新闻价值分） | 不建此字段 |
| 内容出发点 | "今天有什么新闻" | "什么对目标读者有用" |

钉钉表里 98 条命题全部带栏目和目标读者，分布在「一张图看懂」「科研人避坑」「科技前沿」「学生成长」「深圳科技观察」「专家说」「科技周刊」七个栏目下。评分字段在迁移时被明确要求不建——**选题价值不再用一个分数衡量，而是在命题阶段由人决定**。

内容标准也随之改变。总控文档里写给 AI 的定位是"内容编辑部"而不是"文章生成器"，栏目策略围绕读者的实际问题展开（怎么学、怎么避坑、怎么选方向、深圳有什么），而不是围绕热点时效。

伴随这次切换，系统新增了几项能力：定时发布、外源链接转写、本地 Markdown 作为正文唯一真源、预览页改由自建常驻服务提供。

#### 关于原因的说明

从执行记录和数据结构可以确认**发生了什么变化**：新闻抓取停止、评分字段被弃用、命题全部转为人工、服务对象明确为学会读者。

但**现有日志中没有找到明确的决策记录，无法确认这些变化的直接原因**。以上都是对事实的还原，不是对动机的推断。

## 当前工作流

一条命题从入库到发布，完整链路如下：

```text
人工命题（标题 + 栏目 + 目标读者）
    ↓
[每小时 · 撰写轮询]  detect → lock（防重入）
    ↓
命题理解 → 联网研究 → Research Package
    ↓
双平台独立创作（小红书 / 头条各自成稿）
    ↓
分平台配图（SVG 信息图 / AI 场景图，平台前缀隔离）
    ↓
内容质检（平台合规闸门 + 主题占比闸门 + 六维清单）
    ↓
生成外网预览页（图文穿插，两平台分区）
    ↓
写回任务表 → 平台状态置「待审核」→ 群通知
    ↓
────────── 人工审核 ──────────
    ↓
审核通过 → 状态置「审核通过、待发布」+ 填发布日期
    ↓
[每小时 · 发布轮询]  定时判定 → 登录校验 → 浏览器发文
    ↓
回填「已发布」+ 抓取文章链接 → 群通知
```

每轮轮询处理上限 3 条，其余顺延；队列为空时静默退出，不发消息。

### 驳回重写

审核不通过时，人在对应平台填写驳回意见，系统下一轮只重写**被驳回的那一个平台**，另一个平台的标题、正文、配图完全不动。若意见未涉及配图，则沿用原图并按语义补回正文中的合理位置。

这条"平台严格隔离"是硬约束：写回时只提交被改平台的字段。


## 核心设计

### AI 与自动化的分工

| 节点 | 承担者 | 说明 |
|---|---|---|
| 命题 | 人 | 决定写什么、写给谁 |
| 取任务 / 加锁 | 脚本 | 轮询 + 状态锁，防重入 |
| 资料研究 | AI | 联网检索，按来源优先级取信，交叉验证 |
| 写作 | AI | 同一资料包，两平台各自独立成稿 |
| 配图 | AI + 脚本 | SVG 信息图与 AI 场景图，平台前缀隔离 |
| 质检 | 脚本 + AI | 硬闸门交给脚本，软判断交给 AI |
| 预览 | 脚本 | 生成静态页，做图片存在性与排版自检 |
| 审核 | 人 | 唯一的人工放行点 |
| 发布 | 脚本 | 浏览器自动化，含登录态校验 |
| 状态回写 / 通知 | 脚本 | 只在确认真实成功后执行 |

分工的原则是：**判断交给 AI，事实交给脚本，决定交给人**。脚本能确定的事（字数、状态、文件是否存在）不让 AI 判断；AI 该做的事（写什么、怎么组织）不让脚本替代。

### Human-in-the-loop

人工审核不是一个"可选步骤"，而是发布链路上唯一的触发条件。

系统用两阶段闸门保证这一点：

```text
撰写完成 → 平台状态 = 待审核        ← AI 只能写到这里
人工审核 → 平台状态 = 审核通过、待发布  ← 只有人能置这个状态
发布轮询 → 只认「审核通过、待发布」    ← 其他任何状态一律跳过
```

AI 侧的红线是"只写内容、设状态、回填预览链接，绝不发布"。两侧各写一半状态，谁也越不过去。

### 状态驱动

所有行为都由任务表里的状态字段驱动，没有任何"记住上次做到哪"的内存状态：

- `AI生成中` 作为锁，防止同一条被重复处理；
- 失败则回滚到 `待撰写`，下轮重试；
- 重写完成后必须把该平台状态移出"未通过"，否则会无限重写；
- 发布成功才置 `已发布`，抓取链接失败不影响状态回写。

好处是任何一轮中断都不会污染系统状态，重跑是安全的。

### 生产与发布解耦

两条独立的定时任务，各自轮询、各自写自己负责的字段，互不调用：

| | 撰写轮询 | 发布轮询 |
|---|---|---|
| 触发条件 | 完成状态 = 待撰写 | 平台状态 = 审核通过、待发布 且 到发布时间 |
| 产出 | 正文 + 配图 + 预览页 | 平台文章 + 链接 |
| 绝不 | 发布 | 写正文 |

这样一边挂了不影响另一边，也便于分别调频率。

### 平台隔离

小红书和头条的内容、配图、状态字段、浏览器标签页、发布进程全部隔离：

- 正文分别创作，禁止"写一篇再改写成另一篇"；
- 配图文件名带平台前缀，不跨区复用；
- 发布时每个平台跑独立进程，按域名复用独立标签页；
- 新增平台只需在注册表加一条 + 写一个发布脚本，不动编排核心。

## 多平台内容生产

同一命题、同一份资料包，两个平台各自独立成稿。禁止先写头条再缩短成小红书，也禁止反向扩写。

差异是结构性的，不只是字数：

| | 小红书 | 今日头条 |
|---|---|---|
| 结构 | 问题 → 解释 → 图解 → 对比 → 结论 | 标题 → 导语 → 背景 → 分析 → 案例 → 影响 → 总结 |
| 篇幅 | 600–950 字（硬上限） | 800 字以上（过短告警） |
| 标题 | ≤64 字 | ≤30 字 |
| 符号 | 禁止 markdown 语法符 | 需转为富文本层级 |
| 配图 | 竖版卡片式，数量较多 | 横版，服务于阅读节奏 |
| 语气 | 强视觉、易收藏 | 完整、专业、有分析 |

配图遵循"文图不重复"：图是补充视角，不是正文的截图化。清单/避坑类优先手写 SVG 信息图（文字准确、布局可控），场景/人物类用 AI 生成图（中心裁 16:9）。

## 项目中的关键问题与解决

这些是真实发生过、并被修掉的问题，不是设计时的预案。

| 问题 | 根因 | 解决 |
|---|---|---|
| 头条重复发布 3 条 | 成功判定只认 toast 和文章页 URL；实际跳转到列表页，判定为失败 → 不回写 → 下轮重发 | 补列表页跳转信号；**并加发布前标题去重闸门**——不能只靠回写防重 |
| 表状态显示"已发布"但平台没出稿 | 成功信号误判为成功 | 明确成功只认真实信号；状态回写与链接抓取解耦，抓不到链接也回写状态，避免重发 |
| 小红书连挂 4 轮发不出 | 标题框是 `input` 不是 `textarea`，选择器从未命中；确认按钮在 closed shadow root 内 | DOM 快照取坐标 + 真实鼠标点击；标题框模糊匹配 + 回读校验，写不进就终止本轮 |
| 头条正文全部丢失 | ProseMirror 粘贴后约 1.2s 异步变成全选，旧代码在那一刻判断选区已收起 | 粘贴后等异步稳定，再无条件把光标折到文末并强制同步 |
| 封面上传时有时无 | 靠固定 sleep 撞时序，而"确定"按钮是上传成功后才出现 | 改为状态驱动：等抽屉 → 等"已上传" → 等按钮可点 → 校验结果 |
| 预览图全部堆在文末 | 配图文件名用纯编号，语义匹配失败，退化为均匀分布 | 文件名主题段必须用语义词，它同时是预览页插图定位的依据 |
| 12 张手写 SVG 全部渲染失败 | XML 属性值单引号定界，字体列表含逗号导致解析错误 | 属性值一律双引号定界；生成后用浏览器 DOMParser 校验合法性 |
| 91 条任务长期静默跳过 | 文件名相似度用"二元组计数"，高频词就能凑够分 | 改为 Dice 相似度 + 阈值 + 短核心子串兜底，建 13 条回归用例 |
| 预览链接大面积失效 | 托管部署通道不稳定（524 / 沙箱回收） | 改为自建常驻服务 + 反向代理 + 隧道，生成即外网可达 |

最后一个问题的教训被写进了规范：**不要只验证"文件在不在"和"HTTP 200"，要验证"图能不能真的渲染"**。前三道校验（存在性、状态码、HTML 结构）全过，图却全是坏的。

## 项目复盘

### 自动化不是目的

这套系统最花时间的地方，不是"让 AI 写文章"，而是**让链路上的每一步都有明确的成功判定**。

前三周的绝大多数事故，都不是 AI 写错了，而是自动化环节给出了错误的信号：以为发布成功、以为已登录、以为图传上去了、以为这条任务已经处理过。一个错误信号会沿着链路放大——判定失败导致不回写，不回写导致下一轮重发，重发导致平台出现 3 条重复文章。

所以后来定了一条硬规矩：**成功必须是可验证的真实信号，不能是"我点了这个按钮"**。凡是拿不到真实信号的地方，就加一道前置闸门（发布前查重）或后置校验（发完核查实际出稿）。

### AI 与工作流的关系

AI 在链路里承担的不是一个"写作 API"，而是需要处理歧义的中间环节：理解命题、判断资料可信度、决定两个平台怎么分别组织内容、按驳回意见改稿。

但 AI 不适合做两件事：**判定事实**（能不能发、图在不在）和**记住状态**（做到哪一步了）。前者交给脚本，后者交给任务表。

真正让系统能长期跑起来的，是"AI 负责判断，脚本负责事实，表格负责状态"这个分工。

### 为什么业务变化后需要重新设计系统

飞书换钉钉这件事，如果只当成"换数据源"，大概改几个配置项就够了。实际上它触发了三处设计变更：

1. **正文字段没了** —— 钉钉表不存正文，于是正文改为本地 Markdown 作为唯一真源，发布时按平台格式转换；
2. **需要定时发布** —— 新增日期字段和定时判定，未填视为立即发布，解析失败也按立即发布（宁可早发不卡死）；
3. **预览通道要换** —— 从托管部署改为自建常驻服务，因为托管通道不稳定已经让预览链接大面积失效过。

这三件事都不是"迁移"带来的，而是**新业务阶段提出的新要求**：内容要排期发布、审核要稳定可访问、正文要能被脚本可靠读取。

回头看，Phase 1 到 Phase 2 的变化里，换表格是最小的一部分。真正变的是系统的输入（新闻 → 命题）和输出要求（尽快发 → 按计划发），中间那一层不得不跟着重做。

### 还欠的账

- 内容效果数据没有回流，无法判断"哪类命题值得多写"；
- 审核环节没有 SLA，实际吞吐取决于人什么时候打开表格；
- 发布依赖本地常驻浏览器，机器不开就不发。

## 技术栈

| 层 | 选型 |
|---|---|
| 任务与状态 | 多维表格（早期飞书多维表，现钉钉 AI 表格） |
| 编排与执行 | WorkBuddy（AI agent）+ Node.js 脚本群 |

| 质检 | 自研 Node 脚本（平台限制 + 主题占比） |
| 预览 | 静态页 + Docker 常驻服务 + 反向代理 + 隧道 |
| 发布 | puppeteer-core + Chrome DevTools Protocol |
| 通知 | 企业 IM 机器人 |
